# 설계·운영 배경 질의응답

이 문서는 cubrid-dev2-server의 설계 의도와 운영 요구사항에 대한 사용자 답변을 보관한다.

사용자가 답변하면 해당 질문의 답변란에 기록한다.
코드나 기존 문서에서 추론한 내용을 사용자 답변으로 기록하지 않는다.
미답변 항목은 확정된 요구사항이나 설계 결정으로 취급하지 않는다.

## 1. `--privileged`가 필요했던 이유

**질문:** `--privileged`가 꼭 필요했던 이유가 있나요?
이 옵션 없이 실행했을 때 systemd나 cgroup에서 문제가 났나요?
아니면 SystemTap, perf, 디버깅 같은 작업에 필요했나요?
여러 방법을 시도하다가 이 설정에서 정상 동작한 건지도 궁금해요.
LAN 연결을 위한 rootful 실행과는 별개의 선택이라서요.

**답변:**

- 당시 다른 팀의 기존 인프라가 모두 `--privileged`를 사용하고 있었다.
  같은 구성을 따라 개발·디버깅 과정에서 문제가 생기는 것을 피하려고 했다.
- `--privileged` 없이도 사용해 보았으나, strace, GDB, 코어 파일 확인 등의 디버깅 작업에서 권한 문제를 겪었다.
- 사용자는 커널이나 시스템 관련 권한을 컨테이너 생성 시 설정해야 하는 것으로 추정했다.
  필요한 세부 권한과 제한의 정확한 원인은 확인하지 않았다.
- 당시에는 필요한 권한을 개별적으로 검토할 시간이 없었고, AI의 도움도 받을 수 없어 충분히 확인하지 못했다.
  이 상황에서 `--privileged`를 적용했으며, 필요한 최소 권한 조합은 미검토 상태다.

## 2. 컨테이너별 LAN IP의 필요성

**질문:** 컨테이너마다 독립적인 LAN IP가 필요한 이유는 무엇인가요?
CUBRID HA·복제 테스트나 CI 접속에 필요한가요?
아니면 개발자들이 일반 서버처럼 SSH로 접속하고 여러 서비스 포트를 자유롭게 쓰기 위해서인가요?

**답변:** 미답변.

bridge나 macvlan을 사용하다가 겪은 문제가 있었나요?

## 4. VM 대신 컨테이너를 선택한 이유

**질문:** VM 대신 컨테이너를 선택한 가장 큰 이유는 무엇인가요?
메모리 사용량, 빌드 성능, 생성 속도, 관리 편의성 중 무엇이 중요했나요?
서로 다른 커널까지 테스트할 필요는 없나요?

**답변:** 미답변.

실수로 실행한 sudo 명령이나 테스트가 다른 사람에게 미치는 영향도 제한하고 싶은가요?
