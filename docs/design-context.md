# 설계·운영 배경 질의응답

이 문서는 cubrid-dev2-server의 설계 의도와 운영 요구사항에 대한 사용자 답변을 보관한다.

사용자가 답변하면 해당 질문의 답변란에 기록한다.
코드나 기존 문서에서 추론한 내용을 사용자 답변으로 기록하지 않는다.
미답변 항목은 확정된 요구사항이나 설계 결정으로 취급하지 않는다.

## 1. `--privileged`가 필요했던 이유

**질문:** `--privileged`가 꼭 필요했던 이유가 있나요?
이 옵션 없이 실행했을 때 systemd나 cgroup에서 문제가 났나요?
아니면 SystemTap, perf, 디버깅 같은 작업에 필요했나요?
여러 방법을 시도하다가 이 설정에서 정상 동작한 건지도 궁금해요.
LAN 연결을 위한 rootful 실행과는 별개의 선택이라서요.

**답변:**

- 당시 다른 팀의 기존 인프라가 모두 `--privileged`를 사용하고 있었다.
  같은 구성을 따라 개발·디버깅 과정에서 문제가 생기는 것을 피하려고 했다.
- `--privileged` 없이도 사용해 보았으나, strace, GDB, 코어 파일 확인 등의 디버깅 작업에서 권한 문제를 겪었다.
- 사용자는 커널이나 시스템 관련 권한을 컨테이너 생성 시 설정해야 하는 것으로 추정했다.
  필요한 세부 권한과 제한의 정확한 원인은 확인하지 않았다.
- 당시에는 필요한 권한을 개별적으로 검토할 시간이 없었고, AI의 도움도 받을 수 없어 충분히 확인하지 못했다.
  이 상황에서 `--privileged`를 적용했으며, 필요한 최소 권한 조합은 미검토 상태다.

## 2. 컨테이너별 LAN IP의 필요성

**질문:** 컨테이너마다 독립적인 LAN IP가 필요한 이유는 무엇인가요?
CUBRID HA·복제 테스트나 CI 접속에 필요한가요?
아니면 개발자들이 일반 서버처럼 SSH로 접속하고 여러 서비스 포트를 자유롭게 쓰기 위해서인가요?

**답변:**

- 개발자들이 SSH로 접근하는 방식을 선호하며, 컨테이너를 거의 VM처럼 사용한다.
- CUBRID는 여러 포트를 사용한다. 개발자마다 자신의 컨테이너에서 33000번 같은 동일한 포트 번호를
  다른 개발자의 컨테이너와 충돌 없이 사용할 수 있어야 한다.
- 호스트 IP 하나에 컨테이너별로 다른 포트 번호를 배정하는 방식은 요구사항에 맞지 않는다.
  각 컨테이너가 독립적인 LAN IP로 여러 서비스 포트를 사용할 수 있어야 한다.

## 3. ipvlan을 선택한 배경

**질문:** 네트워크 방식으로 ipvlan을 선택한 배경이 있나요?
스위치에서 추가 MAC 주소를 제한했나요?
bridge나 macvlan을 사용하다가 겪은 문제가 있었나요?

**답변:**

- ipvlan이 macvlan보다 더 좋은 방식이라는 이야기를 듣고 선택했다.
  직접 비교하거나 검증하지는 않았다.
- 외부에서 컨테이너로 직접 SSH 접속하려면 "host의 network driver"를 사용해야 하며,
  bridge에서는 이것이 안 된다는 설명도 들었다. 이 설명은 검토가 필요하다고 밝혔다.

### 공식 문서 검토 메모

아래는 사용자 답변과 구분한 공식 문서 확인 결과다. 실제 호스트에서의 검증은 수행하지 않았다.

- 기본 rootful bridge에서도 호스트 IP와 공개한 포트를 통해 외부에서 컨테이너 서비스에 접속할 수 있다.
  이 방식은 컨테이너에 독립적인 LAN IP로 직접 접속하는 방식과 구분해야 한다.
  [Podman 기본 네트워크 가이드](https://github.com/podman-container-tools/podman/blob/main/docs/tutorials/basic_networking.md#bridge)
- `--network=host`는 호스트의 네트워크 네임스페이스를 공유한다.
  ipvlan의 `parent` 옵션으로 호스트의 물리 인터페이스를 지정하는 것과는 다른 설정이다.
  사용자가 들은 "host의 network driver"가 어느 설정을 의미했는지는 미확인이다.
  [Podman 네트워크 모드](https://docs.podman.io/en/latest/markdown/podman-run.1.html#network-mode-net),
  [네트워크 생성 옵션](https://docs.podman.io/en/latest/markdown/podman-network-create.1.html#opt-o-option)

이 서버에서 포트 재할당 없이 독립적인 LAN IP를 제공할 수 있는 bridge 구성의 가능성과
ipvlan·macvlan의 적합성 비교는 추가 검토가 필요하다.

## 4. VM 대신 컨테이너를 선택한 이유

**질문:** VM 대신 컨테이너를 선택한 가장 큰 이유는 무엇인가요?
메모리 사용량, 빌드 성능, 생성 속도, 관리 편의성 중 무엇이 중요했나요?
서로 다른 커널까지 테스트할 필요는 없나요?

**답변:** 구성이 유연하고 여러 CPU 코어를 활용할 수 있으며, 가볍고 관리하기 편해서 컨테이너를 선택했다.

## 5. 개발자 사이에 기대하는 격리 수준

**질문:** 개발자 사이의 격리는 어느 수준까지 기대하나요?
모두 호스트 관리자에 준하는 권한을 맡겨도 되는 사람들이고, 주로 패키지와 작업 환경의 충돌을 막으려는 건가요?
실수로 실행한 sudo 명령이나 테스트가 다른 사람에게 미치는 영향도 제한하고 싶은가요?

**답변:** 개발자가 컨테이너에서 sudo 명령을 잘못 실행했을 때,
다른 개발자의 환경이나 호스트에 미치는 영향까지 막는 것은 필수 요구사항이 아니다.

## 6. 자원 과다 사용에 대한 운영 정책

**질문:** 한 개발자의 빌드가 자원을 과도하게 쓰면 어떻게 처리하고 싶나요?
CPU·메모리 제한을 강제해야 하나요, 아니면 남는 자원을 자유롭게 쓰는 것이 더 중요한가요?
실제로 OOM, SSH 지연, 디스크 부족, 성능 측정 간섭 중 어떤 문제가 있었나요?

**답변:** 한 개발자의 빌드가 CPU나 메모리를 과도하게 사용할 때, 사용량을 제한할 수 있어야 한다.

## 7. 재생성과 재부팅 후 유지할 상태

**질문:** 컨테이너 재생성과 호스트 재부팅 후 무엇이 유지되어야 하나요?
`/home`만 보존하면 충분한가요?
개발자가 설치한 패키지나 `/etc` 설정도 중요한가요?
재부팅 후 자동 시작과 홈 볼륨 백업도 필요한가요?

**답변:** 미답변.
